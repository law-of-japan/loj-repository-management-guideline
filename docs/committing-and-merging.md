# コミットし、マージするとき

作業ブランチを切り、コミットし、PRをマージするときに確かめてほしい規則です。参加する前に、[CONTRIBUTING.md](../CONTRIBUTING.md)を読んでください。従来の形式の既存のリポジトリのブランチについては、[既存のリポジトリの`master`ブランチ](migrating-legacy-repositories.md#既存のリポジトリのmasterブランチ)を参照してください。

## ブランチの取り扱い

- 正本のブランチ（正本ブランチ）は`main`とします。登録台帳のRecordの`repository`にも`main`を記録します。
- mainブランチに直接コミットすることは禁止します。(作業ブランチのPRのマージという形でのみmainブランチの更新が許されます)
- 情報の更新や追加を行うときは、対象となる改正法の日付_番号をブランチ名として新たなブランチを作り、作業完了後にPRを作ってmainブランチへマージします。
- ブランチ名の例: 20190302_31
- mainブランチの各コミットは、[コミットポリシー](#コミットポリシー)に従い、変更の種類を一つだけ宣言します（CHG-03）。
- PRは、mainブランチの履歴が一本になる方法（SquashマージまたはRebaseマージ）で統合します。Mergeコミットを作る方法では統合しません。mainブランチのマージコミットは、変更検査で不合格になります（CHG-03）。
- PRのコミットをSquashマージでまとめてよいのは、まとめるコミットの変更の種類がすべて同じ場合に限ります。種類の違うコミットを含むPRは、コミットを保ったままRebaseマージで統合し、mainブランチに並ぶ各コミットがそれぞれ一つの種類を宣言するようにします。各コミットは、それぞれ単独で変更検査を受けます。
- mainブランチにforce pushしてはいけません。mainブランチのコミットは固定参照の対象であり（FIXREF-04）、履歴を書き換えると既存の固定参照が解決できなくなります。誤りは、新しいコミット（`correction`等）で直してください。
- 作業ブランチのコミットは固定参照に使えません（FIXREF-04）。マージ前のコミットへのリンクを、引用に使わないでください。

### `history`ブランチ（派生ビュー）

- 版を一本の線形なGit履歴として閲覧するための`history`ブランチは、正本から生成器が機械的に作る派生ビューです（VIEW-01）。形式の一例は、仕様の[付録A（historyブランチ）](https://github.com/law-of-japan/loj-spec/blob/main/spec/common/v1alpha1/appendix-a-history-branch.md)にあります。
- `history`ブランチを人が直接編集したり、pushしたりしてはいけません。`history`ブランチの内容を正本に書き戻してもいけません（VIEW-01）。
- `history`ブランチは、正本の`main`から再生成できるものであり、適合の判定や判断の根拠にはなりません（VIEW-07）。先頭の版を「現行」と表示する場合も、選択規則での先頭であることを意味するだけです（VIEW-02）。
- 選択規則で除いた版（施行期日が未確定の版、条件付きの版、併存する版）は、ビューの索引ファイルとコミットのtrailerで示します（VIEW-02）。

## コミットポリシー

まず、基本的にこのプロジェクトでは、該当法令の初回制定から最新の改正が反映された状態まで、各改正時の状態に容易にさかのぼることができるようにすることを目的としています。
各改正時の状態は、history.yamlの版と`versions/<revision_id>/`の版パッケージとして、mainブランチの一つのコミットの中にすべて記録します。従来のように、Gitの履歴を一本に並べて各改正時の状態を表すことはしません（そのような閲覧用の履歴は、`history`ブランチとして派生ビューで作ります）。
mainブランチのGitの履歴は、記録の変更の履歴です。コミットの日時を、公布日や施行日等の法的な時点として扱ってはいけません（HIST-06）。

### 変更の種類の宣言

mainブランチの各コミットは、変更の種類をコミットメッセージのtrailerで宣言します（CHG-03）。

```text
LoJ-Change: revisionAdd
LoJ-Revisions: 98mj5vgx
```

- `LoJ-Change`は、一つのコミットに一つだけ置きます。一つのコミットの変更の種類は一つです。種類を一つに決められない変更は、種類ごとにコミットを分けてください（CHG-01）。
- `LoJ-Revisions`には、対象の版のrevision_idを、カンマと空白（`, `）で区切って並べます。版を対象にしない変更（`format`、登録台帳だけの`metadata`等）では省略できます。
- 種類の宣言を、GitHubのラベル等だけに置いてはいけません。
- 変更の種類は次のとおりです（CHG-01）。

  | `LoJ-Change` | 変更 |
  |---|---|
  | `revisionAdd` | 新しい改正による版を加える。法令の改正に当たるのはこれだけです |
  | `correction` | このプロジェクトの転記・復元の誤りを、原典に照らして直す |
  | `officialCorrection` | 官報正誤による公布本文の訂正を反映する |
  | `restoration` | 欠落していた本文を補う |
  | `metadata` | 本文以外の属性・根拠の更新（施行時点、出典、確認状態、関係、ラベル、字体注記、再構築報告等） |
  | `revisionFix` | 版の取り違えの訂正、版の撤回・統合・分割 |
  | `format` | 同じ内容の表現の変更（Markdownの書式・マーカー・ファイル分割）。本文の字の置換や空白の正規化は含みません |
  | `migration` | 版パッケージを別のschemaVersionへ移す |

- 官報正誤（`officialCorrection`）と転記の誤りの訂正（`correction`）は区別し、どちらも新しい版を作りません（CHG-01）。
- 生成器、CIの設定、文書等、正本のデータに触れない変更は、宣言の対象外です。

### コミットメッセージ

- 作業用ブランチのコミットについては自由に行うことができます。ただし、mainブランチに残るコミットには、上の宣言が必要です。
- 作業用ブランチでの作業を終え、mainブランチにマージする際のコミットメッセージには注意が必要です。
- 以下のようなコミットメッセージを作成することを求めます。

例
>改正 国民の祝日に関する法律の一部を改正する法律 平成三〇年六月二〇日法律第五十七号 (#1)
>
>https://github.com/law-of-japan/20180620-act-57
>
>LoJ-Change: revisionAdd\
>LoJ-Revisions: 98mj5vgx

以上の例はつまり以下のような形式で行うことを示しています。

改廃等の別、半角スペース、根拠法律名、半角スペース、根拠法律の番号、半角スペース、プルリクエスト番号を半角括弧で囲む\
一行開ける\
当プロジェクトの根拠法令のリポジトリのURL（但し、改廃の別が「制定」でない場合で、根拠法令のリポジトリがある場合のみ記述）\
一行開ける\
変更の種類のtrailer

表の行の`key`の付け方の誤り（同じ行に基礎の版と別の`key`を付けた等）を記録訂正（`correction`）で直すときは、直す理由をコミットメッセージに書いてください（TABLE-02）。誤って付けた`key`は、同じ表で再使用しません（TABLE-02、HIST-13）。

コミットメッセージは、閲覧の便宜のためのものです。改正の関係、施行時点、本文を起こした原典資料は、history.yamlの`relations`、`effective`、`text.sources`等に根拠と共に記録してください。コミットメッセージやそのURLを、記録する値の根拠にはしません。コミットメッセージとtrailerはUTF-8で書きます（CHG-03）。

## 法令番号の漢数字での表記

法令番号は、

- 昭和二二年四月七日法律四十九号

のような形式であらわされる。しかし、漢数字の表記法に表記ゆれがみられるため、コミットメッセージ等でこのプロジェクトが書く表記について、ここでそれを統一する。

- 日時を表す漢数字は単に数字を並べるようにして表記する。
  - (例)
  - 〇 昭和二二年
  - × 昭和二十二年
- 番号を表す漢数字は位取りを表す漢数字（十など）も表記する。
  - (例)
  - 〇 法律四十九号
  - × 法律四九号

ただし、原典の表記を記録するデータ（`law.yaml`の`law.number`、登録台帳の番号主張の`raw`、時点値の`raw`等）には、この統一を適用せず、原典の表記をそのまま記録します（CHAR-01、REG-03、TIME-02）。
